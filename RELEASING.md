# First public release

Status: locally prepared, not published. Version: 0.3.2.

## GitHub automation

- **CI** runs on Ubuntu for pushes to main and pull requests, and can also be run manually. It runs clean installation, dependency auditing, the 19 tests, browser geometry checks, build and package-content validation, then uploads an installable `.tgz` artifact.
- After a successful **push to main**, CI creates a GitHub release named after `package.json` (for example `v0.3.2`) and attaches the exact tested archive. Existing releases are left unchanged; increase the package version to create another. Pull requests, manual CI runs and reusable CI calls do not create releases. These GitHub releases are experimental until live Lens testing is complete.
- **Release** handles npm publishing separately. It repeats CI, checks tag/version agreement and Lens dependency compatibility, then publishes to npm. Prerelease versions use npm's `next` tag and GitHub's prerelease flag.
- Running **Release** manually is a dry run by default. To publish an existing CI-created tag, run `gh workflow run release.yml --ref v0.3.2 -f publish=true`. Publishing requires a version tag matching `package.json`. A manually pushed version tag also starts publishing. GitHub does not start another workflow for a tag created with its automatic workflow token, so CI-created releases require the explicit publishing step.
- Release verification still requires the real Lens baseline, so a missing baseline produces an explicit failure. Manual verification without the publish option never publishes or creates a GitHub release.
- Ordinary CI can build without a Lens baseline, with the build tool's explicit skip message. It does not certify Lens compatibility. Once the baseline is committed, CI checks against it too.

### One-time release setup

1. Copy the actual `extension-dependency-versions.json` generated by the Lens installation being tested into `.github/lens-extension-dependency-versions.json`. Commit that file after completing live Lens tests. Do not substitute the lockfile or invent dependency versions. Refresh it and repeat testing after changing the supported Lens version.
2. On npm, open the package's **Settings > Trusted Publisher**, choose **GitHub Actions**, and configure user **u7er**, repository **lens-rowcraft**, workflow filename **release.yml**. Leave the environment name blank: this workflow does not use a GitHub environment. Allow direct `npm publish`. No npm token secret is needed. If the package does not yet exist and these settings are unavailable, bootstrap the first release using your signed-in npm account after all checks pass, then configure trusted publishing for later versions.
3. Ensure GitHub Actions is enabled for the repository. In **Actions > Release > Run workflow**, run the dry run and check its artifact. npm authentication itself is exercised only on a real tag release; dry runs cannot certify account configuration.
4. When ready to release, ensure the package version is new, commit all release files, and push that commit to main. CI creates the GitHub release and tag. After reviewing that release and completing npm setup, explicitly run the publishing workflow on its tag as described above.

The workflow uses npm trusted publishing as described in the [official npm documentation](https://docs.npmjs.com/trusted-publishers). It does not bypass Lens's publishing guard.

## Before publication

1. Make the linked GitHub repository public, or update the repository, homepage and issue URLs to the intended public location. Push the prepared files after reviewing them.
2. Use Lens Plus, Pro, Enterprise or an active trial. Launch the intended Lens version so it generates its extension dependency-version file.
3. Run `npm ci`, `npm run check`, and `npm run prepublishOnly` on that machine. On Windows use `npm.cmd`. Resolve dependency-range mismatches against the actual Lens installation, then rebuild and repeat the checks.
4. Run `npm pack`, and install the resulting `lens-rowcraft-0.3.2.tgz` using Lens's extension installer if it accepts archives. Otherwise extract it and use Install from File System to select the extracted `package/package.json`. Keep that folder in place.
5. Verify the following in live Lens and record OS and exact Lens version:
   - Pods, Deployments, DaemonSets, StatefulSets, ReplicaSets, ReplicationControllers, Jobs and CronJobs.
   - Large-list scrolling to the end; sort, filter, namespaces, visible columns, row selection, detail links, actions and tab changes.
   - Editor field placement, widths, presets, auto width, Apply and Cancel.
   - Independent layouts per workload type; saved layouts and enabled state survive restart and switching clusters.
   - Toggle off, disable and uninstall restore normal rows. Unsupported views remain unchanged.
6. Verify Lens accepts the SVG icon/banner metadata in the Publish dialog. Public documentation confirms npm discovery but does not specify all asset validation rules. Correct these if the installed Lens validator requests another format or size.
7. Update README compatibility evidence after successful live tests. Keep the experimental/internal-adapter disclosure. Remove the "not published yet" sentence as part of the final release preparation.

## Account and publishing steps

1. Create or sign in to the npm account that should own this package. Complete any email verification and account security prompts. Never paste credentials into repository files or chat.
2. Confirm `lens-rowcraft` is still available, or that your account owns it. If the name must change, update package.json, package-lock.json and installation documentation together.
3. Use the configured tag-triggered GitHub Release workflow, or Lens's Publish dialog. For an initial CLI release, sign in with `npm login`, verify the identity with `npm whoami`, then publish from this repository with `npm publish --access public` only after all checks above pass. Do not publish the tarball directly to bypass the source project's lifecycle guard.
4. Confirm the package appears on npm, then search the Lens Marketplace after indexing. Lens says this normally takes minutes.
5. Install from Marketplace in a clean Lens setup. Check publisher identity, description, README images, icon/banner, activation and removal.
6. The tag-triggered workflow creates GitHub release notes and attaches the archive. Add the exact tested Lens version and known limitations to those notes. If the initial release was published manually, create its GitHub release manually too; do not trigger the publishing workflow for an already published version. Future npm releases need a new version; published versions cannot be reused.
